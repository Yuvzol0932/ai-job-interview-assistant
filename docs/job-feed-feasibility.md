# 岗位招聘信息拉取功能 · 可行性分析

> 日期：2026-08-13
> 状态：已确认；第一阶段（种子数据 + 匹配 + 两处展示）已实施
> 关联需求：从公众号/网站拉取与简历匹配的岗位招聘信息，在简历分析界面展示可投递岗位，并提供独立的"企业招聘"板块。

---

## 1. 需求拆解

| # | 需求点 | 说明 |
|---|--------|------|
| 1 | 数据源 | 从微信公众号 或 招聘/就业网站 拉取岗位招聘信息 |
| 2 | 岗位匹配 | 与用户上传的简历内容对应，筛出"可投递"岗位 |
| 3 | 展示点 A | 简历上传后的分析界面（现有"简历诊断"结果区）内嵌展示 |
| 4 | 展示点 B | 独立的"企业招聘"板块（新页面，功能一致，可浏览/筛选全部岗位） |

结论先行：**整体可行，但数据源策略需要调整预期**。"直接爬公众号"在技术和合规上都走不通，建议采用"本地种子数据 + 轻量网站抓取 + 可插拔数据源接口"的分层方案。匹配与展示两部分技术风险低，与现有架构契合度高。

---

## 2. 数据源可行性（本需求的核心难点）

### 2.1 公众号渠道：不推荐直接抓取

| 路径 | 可行性 | 问题 |
|------|--------|------|
| 微信官方 API | 不可行 | 只能管理自己主体的公众号，无法读取他人公众号文章 |
| 搜狗微信搜索等爬虫 | 高风险 | 验证码、IP 封禁频繁，稳定性差；违反微信软件许可协议 |
| 第三方数据服务（新榜、清博等） | 可行但贵 | 付费、以数据 API 为主，非招聘原文 |
| 公众号转 RSS（feeddd / WeRSS 类） | 勉强可用 | 免费服务不稳定，适合作为可选源 |
| 手动维护目标公众号文章链接 | 可行 | 有录入成本，但完全合规，适合演示与冷启动 |

结论：公众号不作为第一版的核心依赖，最多保留"RSS 源"和"手动录入链接"两个可插拔入口。

### 2.2 网站渠道：分源评估

| 来源 | 抓取难度 | 合规风险 | 适用性 |
|------|----------|----------|--------|
| BOSS 直聘 / 前程无忧 / 智联 | 高（登录墙、接口加密、滑块） | 高（用户协议禁止，有不正当竞争判例） | 不建议 |
| 实习僧 / 牛客 | 中高 | 中高 | 不建议第一版碰 |
| 高校就业信息网 | 低（公开页面、结构简单、反爬弱） | 低 | **强烈推荐**，与校招场景天然匹配 |
| 企业官方校招页（腾讯/字节等官网） | 中（逐站适配） | 低-中 | 可挑 1-2 家做样板 |
| 24365 国家大学生就业服务平台 | 中 | 低 | 可作为权威补充源 |
| 第三方招聘数据 API（聚合数据等） | 低 | 低（已获授权的数据服务） | 后续版本可付费接入 |

合规底线：不碰需要登录的数据、遵守 robots 协议、控制请求频率、只采集岗位公开信息（不涉及求职者个人信息，个保法风险低；主要风险是不正当竞争，避开大厂平台即可大幅降级）。

### 2.3 推荐的数据分层架构

- 数据源插件层（统一 Fetcher 接口）
  - 本地种子数据（data/jobs_seed.json）★ 必备
  - 高校就业网抓取器（1-2 个样板）
  - RSS 源（公众号转 RSS，可选开启）
  - 手动录入源（运营/用户粘贴链接解析）
- 聚合与缓存层 services/job_aggregator.py：统一 JobPosting 模型 → 本地 JSON 缓存（带过期）
- 匹配层 services/job_matcher.py：规则过滤（岗位方向/城市/关键词）+ LLM 打分

"本地种子数据"是硬要求而非降级方案——PRODUCT.md 明确"演示流程应不依赖公网也能完整展示"，与现有 LLM mock 模式是同一思路：离线时展示真实风格的内置数据，联网时叠加实时抓取结果。

## 3. 岗位匹配可行性：风险低

现有诊断流程已具备两个可复用资产：

1. `target_job` 岗位方向选择（services/job_catalog.py 已有 7 类岗位方向常量）；
2. 诊断输出中已有"岗位要求对照表"（requirement_table），说明模型已在做简历与岗位的对照推理。

匹配分两级实现：

- **规则过滤（必做）**：按岗位方向、目标城市、关键词（技能词）对岗位库过滤排序。纯 Python，可单测，离线可用。
- **LLM 匹配打分（增强）**：把简历摘要 + 候选岗位列表交给模型，输出 match_score、match_reasons、gap_hints。完全复用现有 llm/client.py + call_chat + mock 兜底机制，断网时退化为规则排序结果。

## 4. 与现有架构的集成点

### 后端（FastAPI）

| 新增 | 职责 |
|------|------|
| models/job.py | JobPosting 数据模型（公司、岗位、城市、薪资、要求、截止时间、来源、链接） |
| services/job_aggregator.py | 数据源插件管理、抓取、去重、本地 JSON 缓存（沿用"无数据库"约束，参考 report_store.py 的文件存储模式） |
| services/job_matcher.py | 规则过滤 + LLM 打分 |
| api/routers/jobs.py | GET /api/jobs（全量/筛选，服务企业招聘板块）、POST /api/jobs/match（按简历文本匹配，服务分析界面） |
| data/jobs_seed.json | 30-50 条真实风格种子岗位（虚构公司，符合"不虚构商业数据"原则） |

新增依赖仅 beautifulsoup4（解析 HTML）；httpx 已在 requirements.txt 中。

### 前端（React）

| 改动 | 位置 |
|------|------|
| 诊断结果区下方新增"可投递岗位"卡片列表 | web/src/pages/ResumeDiagnosis.tsx |
| 新页面"企业招聘"（浏览/按方向城市筛选/查看匹配度） | 新增 web/src/pages/Jobs.tsx，App.tsx 加 /jobs 路由 |
| 导航加"企业招聘"入口 | web/src/components/Layout.tsx navItems |
| API 客户端加 jobs() / matchJobs() | web/src/lib/api.ts |

视觉上复用现有 Card / Button / PageHeader 组件与设计 token（浅蓝条纹 + 鎏金细线），无需新增设计语言。

### 演示兜底

- 断网 / 无 LLM 额度：种子数据 + 规则匹配即可完整走通两处展示；
- GET /api/jobs 永远有数据返回（缓存 → 种子），前端无需处理空态以外的异常分支。

## 5. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 公众号抓取被封/违规 | 高 | 不做直接抓取；只保留 RSS/手动录入口子 |
| 商业招聘平台反爬与诉讼风险 | 高 | 不抓 BOSS/智联等；数据源限定公开就业网与企业官网 |
| 演示现场无公网 | 中 | 种子数据兜底，与 mock LLM 同策略 |
| 岗位数据过期（已截止） | 中 | 缓存带 TTL + 每条岗位存发布时间/截止日期，过期标注或过滤 |
| 抓取的岗位要求文本质量参差 | 中 | 入库前用规则清洗 + 可选 LLM 摘要规整 |
| 隐私合规 | 低 | 简历原文不落库原则不变；匹配请求只传摘要，岗位数据本身非个人信息 |

## 7. 实施建议（分阶段验收）

1. **第一阶段（演示就绪）**：P0+P1，纯种子数据即可交付完整体验——上传简历，分析结果下方出现"可投递岗位"（含匹配度与理由）；导航出现"企业招聘"板块，可筛选浏览。验收标准：断网状态下全流程可演示。
2. **第二阶段（真实数据）**：P2 接入 1 个高校就业网抓取器与可选 RSS 源，验证缓存与去重。验收标准：联网时岗位列表出现实时数据并标注来源。
3. **第三阶段（按需）**：付费招聘数据 API 或校企合作授权数据源，替换/补充抓取器。

---

## 8. 总结

| 子需求 | 可行性结论 |
|--------|-----------|
| 从**公众号**拉取 | 直接抓取不可行（无公开 API、反爬、违规）；可用 RSS/手动录入作为可选源 |
| 从**网站**拉取 | 可行，但数据源应选高校就业网/企业官网等公开低反爬站点，避开商业招聘平台 |
| 简历与岗位匹配 | 技术成熟，规则 + LLM 两级方案与现有架构无缝兼容 |
| 分析界面展示可投递岗位 | 纯前端 + 一个 API，改动小 |
| 独立企业招聘板块 | 新页面 + 复用同一 API，改动小 |

**建议立项**，按第 7 节分阶段推进；第一阶段的范围不依赖任何外部数据源，风险可控。
