# 开发规范

## 一、目录与命名

- 目录结构固定为：`ui/`（界面层）、`services/`（业务层）、`llm/`（模型接口层）、`models/`（数据结构）、`docs/`（文档）、`tests/`（测试）。
- 模块名、文件名统一小写加下划线（如 `resume_parser.py`）。
- 每个模块只做一件事；禁止界面层直接调用模型接口层。

## 二、Git 提交规范

- 主分支 `main`，每完成一个模块或修复一个问题提交一次。
- 提交信息使用语义化前缀：
  - `feat:` 新功能
  - `fix:` 修复
  - `docs:` 文档
  - `refactor:` 重构
  - `test:` 测试
  - `chore:` 构建或杂项
- 示例：`feat: 实现简历 PDF 解析`、`fix: 修复报告分数越界`。
- 里程碑完成时打标签：`v0.1`、`v0.2`、`v0.3`。

## 三、密钥与隐私规范

- API 密钥只放 `.env`（本地）或部署平台的密钥区，**绝不写入代码**。
- `.env`、`.streamlit/secrets.toml`、`data/reports/` 已加入 `.gitignore`，禁止强制提交。
- 简历原文不写入任何数据库；报告仅保存在本地。

## 四、AI 协作约定（vibe coding 准则）

1. **架构优先**：任何新功能先确认它属于哪一层、接口契约是什么，再写代码。
2. **文档同步**：开发文档与代码同步更新，完成一步勾一步。
3. **防自嗨**：每个里程碑结束必须调研行业最佳实践，对照后修订路线图。
4. **问题先跳出来**：遇到 bug 或方向困惑，先查最佳实践再动手，禁止闷头硬改。
5. **可预期**：每次调用输入输出都要符合契约；契约变更必须同步更新架构文档与测试。

## 五、测试约定

- 业务层必须可独立测试（不依赖界面和网络）。
- 模型调用在测试中用假客户端替换，禁止测试消耗真实 API 额度。
- 提交前必须通过 `python -m pytest tests -q`。
